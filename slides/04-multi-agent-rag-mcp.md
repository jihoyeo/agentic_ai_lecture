# 멀티 에이전트 — 오케스트레이터 + 서브에이전트

```
                  사용자 질문
                      │
                      ▼
              [ 오케스트레이터 ]   ← 질문 종류를 판단해 분배
               │               │
       "시뮬레이션 해줘"     "데이터 분석해줘"
               │               │
               ▼               ▼
       시뮬레이션 전문가      분석 전문가
        서브에이전트          서브에이전트
```

- **오케스트레이터** — 받아서 *누구에게 맡길지* 정한다
- **서브에이전트** — 각자 자기 도구만 갖고 한 분야를 잘한다

---

# 라우팅 패턴

오케스트레이터가 하는 일은 결국 **분류 + 위임**:

```python
def orchestrator(question):
    kind = classify(question)          # LLM에게 종류를 묻는다
    if kind == "simulation":
        return simulation_agent(question)
    elif kind == "analysis":
        return analysis_agent(question)
    else:
        return "답변할 수 없는 질문입니다."
```

- `classify` 도 작은 LLM 호출 하나로 처리할 수 있다.
- 각 서브에이전트는 S3의 **그 에이전트 루프** 그대로다.

---

# 사례 — DTUMOS 의 두 에이전트

DTUMOS는 역할을 둘로 나눕니다:

| 에이전트 | 역할 |
|---|---|
| **Orchestrator** | 사용자 의도 파악 → 시뮬레이션 실행 |
| **Interpreter** | 시뮬레이션 결과를 분석·해석해 설명 |

```
"대전 택시 50대 시뮬레이션하고 결과 해석해줘"
   → Orchestrator: run_simulation(...) 실행
   → Interpreter:  결과 지표를 받아 의미를 설명
```

> "실행"과 "해석"을 분리 — 각자 더 잘하게.

---

# RAG — 에이전트에게 "지식"을 주기

LLM은 우리 조직 문서, 최신 정보를 모릅니다 (한계 ②).

> **RAG (Retrieval-Augmented Generation)**
> = 질문과 관련된 문서를 **검색**해서, 프롬프트에 **넣어 주고**, 그걸 근거로 **답하게** 하기

- "학습"시키지 않는다 — 답할 때 **참고자료를 쥐여 준다**.
- 환각이 줄고, 출처가 분명해진다.

---

# RAG — 흐름

```
   질문:  "DTUMOS가 뭐야?"
      │
      ▼
   ① 검색   knowledge.json 의 청크 중 'DTUMOS' 관련을 찾는다
      │
      ▼
   ② 주입   찾은 청크를 프롬프트에 함께 넣는다
            "[참고자료] DTUMOS는 ... 이다.  /  질문: DTUMOS가 뭐야?"
      │
      ▼
   ③ 생성   LLM이 그 참고자료에 근거해 답변
```

- 핵심 준비: 문서를 **청크(chunk)** 로 잘게 나눠 두는 것.

---

# RAG 도 결국 "하나의 도구"다

검색을 **도구**로 만들면, RAG가 에이전트 루프에 자연스럽게 들어온다:

```json
{ "name": "search_docs",
  "description": "프로젝트 문서에서 질문과 관련된 내용을 검색한다.",
  "parameters": { "type": "object",
    "properties": { "query": { "type": "string" } } } }
```

- 에이전트는 모르는 게 나오면 `search_docs` 를 부른다 → 결과를 관찰 → 답한다.
- S2~S3에서 배운 구조 그대로 — **새 개념이 아니라 새 도구**.

---

# MCP — Model Context Protocol

도구를 만들 때마다 매번 새로 연결하긴 번거롭다.

> **MCP** = 도구·데이터를 LLM에 연결하는 **표준 규격**

```
   [ 우리 도구들 ]  ──MCP 서버로 감싸기──→  표준 인터페이스
                                              │
              ┌───────────────┬───────────────┤
              ▼               ▼               ▼
        Claude Desktop   우리 에이전트     다른 앱
```

- 한 번 MCP 서버로 만들면, **여러 클라이언트가 재사용**한다.

---

# MCP — 왜 필요한가

- USB-C 에 비유: 기기마다 다른 충전기 → **하나의 표준 포트**
- 도구를 만든 사람과 쓰는 사람이 **분리**된다 → 생태계가 자란다
- 사례: **DTUMOS의 MCP 서버**
  - 시뮬레이션 기능을 MCP로 노출
  - Claude Desktop 등에서 *바로* "대전 시뮬레이션 돌려줘" 가능

> 도구를 "우리 코드 안의 함수"에서 "누구나 꽂아 쓰는 부품"으로.

---

# 평가 — 에이전트가 잘 동작하는가?

에이전트는 LLM 때문에 **실행할 때마다 답이 다르다**. 어떻게 검증할까?

문제: 진짜 LLM은
- 호출마다 결과가 **달라진다** (비결정적)
- **비용**이 들고 **느리다**
- 네트워크가 필요하다

> → 테스트하려면 **예측 가능한** LLM이 필요하다.

---

# Mock LLM 으로 결정론적 테스트

**가짜 LLM** 에 "이렇게 응답하라"는 대본을 미리 준다:

```python
scripted = ScriptedLLM([
    LLMResponse(tool_calls=[ToolCall("get_top_flows", {"n": 3})]),
    LLMResponse(text="가장 큰 통행은 송파구→강남구입니다."),
])
agent = Agent(llm=scripted, tools=...)
result = agent.run("...")
assert "송파구" in result        # 항상 같은 결과 → 테스트 가능
```

- 네트워크·비용 0, 같은 입력에 **늘 같은 출력**.
- DTUMOS도 `test_agentic_engine.py` 에서 이 방식으로 에이전트를 테스트한다.

# 안전 · 가드레일(Guardrails)

에이전트는 도구로 **실제 행동**을 한다 — 안전장치가 필수다.

| 위험 | 가드레일 |
|---|---|
| 코드 실행 도구 | **샌드박스**에 격리 |
| 멈추지 않는 루프 | `MAX_STEPS` 상한 (S3) |
| LLM 호출 비용 폭증 | 호출 수·토큰 **모니터링** |
| 위험한 작업 (삭제·결제) | **사람의 승인** 요구 |

> 강력함과 안전은 함께 간다 — 에이전트를 *풀어놓되, 울타리 안에서*.
